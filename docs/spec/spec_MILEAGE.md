# Spec MILEAGE: правило «пробег не больше 400 000 км»

Источник требований: `docs/intent/intent_MILEAGE.md`. Всё, что ниже, либо взято
из intent, либо явно помечено как Open question. Новых требований сверх intent нет.

## Входит / не входит

### Входит

- Изменение `DecisionEngine`: при пробеге свыше порога решение понижается
  с `approve` до `review`.
- Пробег передаётся в `DecisionEngine` (правка `AppFactory` / сигнатуры решателя).
- Новый ключ `vehicle.mileage_review_max_km = 400000` в `backend/config/rules.php`.
- Тесты: граничные значения пробега (399 999 / 400 000 / 400 001) и пустой пробег.

### Не входит

- Фронтенд, БД, репозиторий.
- `ltv_by_age` (LOAN-12).
- Сравнение «одометр против слов клиента» (CASE-08 / client_note).
- Валидационный предел `max_mileage_km = 500000` — другая величина с другой
  семантикой («вообще не принимаем»), не трогаем.
- Поле причины решения в ответе API — решение остаётся без объяснений.

## Требования

### REQ-MILEAGE-01: порог пробега

Порог понижения решения задаётся конфигом `vehicle.mileage_review_max_km = 400000`
в `backend/config/rules.php`, а не хардкодом в коде.

- AC-MILEAGE-01: в `backend/config/rules.php` присутствует ключ
  `vehicle.mileage_review_max_km` со значением `400000`. Числа в коде
  `DecisionEngine` нет.
- Источник числа 400 000: формулировка задачи в intent, «порог решения»;
  `vehicle.max_mileage_km = 500000` — валидационный предел, остаётся без изменений.

### REQ-MILEAGE-02: граница «не больше 400 000»

При LTV в зелёной зоне (approve по LTV):

- AC-MILEAGE-02: mileage = 399 999 → `approve`.
- AC-MILEAGE-03: mileage = 400 000 → `approve` (граница включительная,
  «не больше» = `<=`).
- AC-MILEAGE-04: mileage = 400 001 → `review` с `approved_limit = 0`.
- Источник: intent, «Принятые решения», строка «Граница 400 000»; подтверждено
  риск-менеджментом — см. Open question OQ-1.

### REQ-MILEAGE-03: правило только понижает approve → review

Правило пробега применяется только к ветке `approve` по LTV. Ветки `review`
и `reject` по LTV не меняются: высокий пробег не превращает review в reject,
а «зелёный» LTV при высоком пробеге не остаётся approve.

- AC-MILEAGE-05: LTV-ветка review + mileage 450 000 → `review` (не reject).
- AC-MILEAGE-06: LTV-ветка reject + mileage 10 000 → `reject` (пробег не
  «спасает» от reject).
- AC-MILEAGE-07: LTV-ветка approve + mileage 400 001 → `review`
  (не approve, не reject).
- Источник: intent, «Взаимодействие с LTV»; см. OQ-2.

### REQ-MILEAGE-04: пустой или неизвестный пробег

Пустой/отсутствующий пробег не доходит до `DecisionEngine`: существующая
валидация в `ApplicationValidator` отклоняет заявку.

- AC-MILEAGE-08: mileage отсутствует / null / пустая строка → `ValidationException`
  с сообщением «Пробег от 0 до 500000». Решение не вычисляется.
- Источник: intent, «Пустой пробег» — существующее поведение без изменений;
  см. OQ-3.

### REQ-MILEAGE-05: ответ API без причины

В ответе API не появляется новое поле причины понижения — формат ответа
не меняется.

- AC-MILEAGE-09: ответ при `review` из-за пробега не содержит новых полей
  относительно текущей схемы ответа.
- Источник: intent, «Причина решения»; см. OQ-4.

## Open questions (перенесены из intent)

Intent помечает все пять принятых решений как неподтверждённые заказчиком
(«не знаю / решай сам») и требует подтверждения риск-менеджментом. Они не
закрыты и перенесены сюда; спека реализуема, но числа и поведение ниже
могут измениться после подтверждения:

1. **OQ-1** — включительность границы 400 000 (400 000 → approve или review?).
   Сейчас в спеке: включительно (`<=`).
2. **OQ-2** — не ужесточает ли высокий пробег review → reject. Сейчас: нет.
3. **OQ-3** — поведение при отсутствии пробега (сейчас — отказ на валидации).
4. **OQ-4** — не нужен ли код причины понижения в ответе API. Сейчас: не нужен.
5. **OQ-5** — место порога (новый ключ в `rules.php` против иного источника).
   Сейчас: новый ключ `vehicle.mileage_review_max_km`.

## Критерий готовности

При LTV в зелёной зоне: mileage 400 000 → approve; 400 001 → review
с `approved_limit = 0`. Ветки review/reject по LTV не меняются.
(Источник: intent, «Критерий готовности».)
